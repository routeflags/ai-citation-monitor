## 0. 結論

Lean 4（定理証明器）をこのリポジトリのビルドと CI に常設する提案は、**いまの失敗モードに対して
費用が見合わない**。理由は 3 点に集約される。（算術は後日、範囲を限定して D21 で採用した。）

1. **Go から Lean への橋がない。** Lean の定理は、Lean で書いた*モデル*についての定理であり、
   `internal/domain` や `internal/analysis` の Go 実装についての定理ではない。両者を結ぶのは結局
   テストベクタであり、それは今あるテストと同じ仕事をする。Rust には Aeneas のような
   コード→Lean の翻訳系があるが、Go 側で知られているのは Goose（Go の一部を Coq に写す）であり、
   対象は並行プリミティブの部分集合で、Lean ではない。
2. **このプロジェクトで面白い部分は Lean に無い。** 意味を持つのは NFKC（`golang.org/x/text`）、
   IDNA / punycode（`golang.org/x/net/idna`）、`net/url` の解析、公開サフィックス判定で、
   これらはどれも Lean の標準ライブラリにも Mathlib にも無い。モデルでは公理として仮定するしかなく、
   **バグが住んでいる場所を仮定して証明することになる**。
3. **Lean は反例を出さない。** このリポジトリで欲しいのは「壊れる操作順の具体例」であり、それは
   モデル検査器（TLC）の仕事。Lean の失敗は「証明が通らない」という形でしか出ず、
   再現手順にならない（D8 の率の定義や、追記専用の破れを Lean で見つける筋が無い）。

一方で Lean が効くのは「算術の恒等式」と「将来の検証済みコアを共有する」場合である。
このうち **算術は初版で軽く扱いすぎた**。レポートは `20.0% (n=1/5)` の形で式そのものを表示しており、
§1 に挙げる恒等式は読者が手で検算できる。Lean のモデルが最も忠実になるのもこの領域で、
とくに**丸め**は「シェアは合計 100%」という誤った主張を正せる唯一の手段になる。ただし危険の中心は
依然として*分母の選択*と*グループ横断*で、その 2 つは定理にならない。

## 1. 証明したいことの棚卸し

「証明したい」対象を先に固定する。Lean が届くかは対象ごとに違う。

| 候補 | 現在の担保 | Lean で書けるか | 備考 |
|---|---|---|---|
| 率の算術（`analysis.NewRate` / `Delta`、`0 <= v <= 1`、`n=0` は未測定） | `metrics_test.go` の表 | 書ける（モデルも忠実） | 恒等式の一覧は下の小節。危険の中心は*分母の選び方*（D8）で、それは定理にならない |
| 「率はグループを越えて合算しない」 | `report` のテスト、レビュー | 書きにくい | 出力の性質であり、`Group` の構成規則の話。型か検査で担保する領域 |
| `CanonicalHost` の冪等性 | 一部のテスト | 書ける（ただしモデル上） | 実際の関数は IDNA に委譲。Lean には IDNA が無い |
| `IsOwnDomain` のラベル境界（`notexample.com` は一致しない） | `domain_test.go` | 書ける | 文字列接頭辞の性質なので、Lean のモデルでも証明は容易。だがテストと同等の保証 |
| `SplitCitationURL` の重複排除キーの安定性 | `domain_test.go` | 書ける（ただしモデル上） | `net/url` の挙動を公理化する必要がある |
| `plan_key` の一意性 | SQLite の `UNIQUE` | 書けない | SHA-256 の衝突困難性を仮定する話で、定理ではない |
| 追記専用（UPDATE を発行しない） | レビュー、`verify` | 書けない | コードの性質。TLA+ か lint（SQL 文字列の検査）の領域 |
| 再送しない／resume の意味（`--session`） | `runner_test.go`、`UNIQUE` 制約 | 書けない | 操作順の性質。**TLC が得意な形** |
| `aicm verify` が見る整合性 | `verify` のテスト | 書ける（モデル上） | DB の状態機械なので TLA+ のほうが自然 |
| export の列（D19） | ゴールデンテスト | 書けない | 契約の話。テストと決定記録が正しい道具 |

読み取れること: Lean が自然に届くのは率の算術と丸めだけ。ただし**いまのテストは代表例を並べたもので、
「合計が一致する」という主張をしているテストは無い**（`metrics_test.go` は値の例を見る）。

### レポートに出る数式と、成立する恒等式

レポートの数値はすべて `internal/analysis` の `Rate`（`N`・`D`・`Value`・`Text`）で、
表示は `NewRate` の `fmt.Sprintf("%.1f%%", value*100)` と `Display` の `RateFormat` だけを通る。
つまり画面上の `20.0% (n=1/5)` は 5 件中 1 件のヒットであり、**百分率と n/d は同じ値の 2 表現**になる。
ここで読者が検算できる等式は次のとおり。

| # | 式 | いまの担保 | 崩れ方 |
|---|---|---|---|
| I1 | 測定済みの率は `0 <= N <= D`（つまり 0〜100%） | 各呼び出し元で分子と分母を同じ集合から取る | 分子を unknown を含む run 集合から取る／分母を success 全件にする |
| I2 | `Text = round1(100·N/D)` | `NewRate` が `Value` から `Text` を作る（再計算しない） | 外で百分率を組み立てる（`analysis` 以外で `%.1f%%` を書かない） |
| I3 | `Σ PerQuestion.N = CitedOwn.N`、`Σ PerQuestion.D = CitedOwn.D` | 同じ `judgedRuns` を質問別に分けて数える（`Build`） | 質問別から unknown を除き忘れる／repeat を二重に数える |
| I4 | `Σ DomainShare.Count = CitationTotal`（ホスト不明も 1 件） | `buildDomains` が同じ `citations` を数える | malformed を捨てる（`SplitCitationURL` が「捨てない」理由） |
| I5 | `covered ⊆ judged`、`judged`・`unmeasured`・`unknownOnly` は互いに素、`roster` の各質問はその 3 つのどれかに入る（`unknownOnly` は roster 外の質問も含む） | `buildCoverage` の 3 つの map | unknownOnly と judged の両方に入る（コードは `!judged[key]` で除く） |
| I6 | シェア列の丸め後の合計は 100.0% でなくなり得る（k 行で 100 ± 0.05k pt） | 丸めは表示だけ | 「合計は 100%」と書いた瞬間に崩れる（**書かない**のが正しい） |
| I7 | ドメイン別獲得率の列は 100% を超え得る（分母は run、シェアの分母は引用件数） | `competitorNote`・`shareNote` の注記 | 2 つの分母を同じ表で混同する |
| I8 | `Σ group.RunsTotal = Totals.RunsTotal`、`RunsTotal = success+error+cancelled`、`RunsUnknown` は観測が `unknown` の run 数（status を問わない） | `buildTotals`（件数はグループをまたいで合計してよい） | 未知の status 値が現れると和が合わなくなる。`RunsUnknown` は失敗 run も含むので `RunsUnknown <= RunsSuccess` ではない |
| I9 | `Delta` は percentage point: `Delta(a,b) = -Delta(b,a)`、`Delta(a,a) = 0`（測定済み）、`Delta(a,c) = Delta(a,b)+Delta(b,c)` | `Delta` の実装と比較・トレンドのテスト | 比率（%）として差を解釈する |

丸めの実測値（Go の `%.1f` は十進で正しく丸め、ちょうどの .5 は偶数丸め）:

- `1/5` → `20.0%`、`1/3` → `33.3%`、`2/3` → `66.7%`、`3/10` → `30.0%`
- `1/16` → `6.2%`（*6.3% ではない*。6.25 の .5 が偶数側に倒れる）、`3/16` → `18.8%`
- 等しい 3 ドメインのシェア `33.3% + 33.3% + 33.3% = 99.9%`、1/7 が 7 行なら `14.3% × 7 = 100.1%`（I6）

読み分け: **I1・I3・I4・I5・I7・I8 は「どの集合を分子と分母にするか」という構成の性質**で、
定義を変えれば崩れる。Lean で書いても「n <= d」「同じ集合を数える」を*仮定*した定理になるだけで、
その仮定が成り立つかは実装の話（だからテストが主役になる）。**I2・I6・I9 は算術そのもの**で、
Lean が届くのはこちら。とくに I6 は「シェアは合計 100%」と主張しないための根拠になる。

現状の手当てを正確に言うと: I4・I5・I7 は `docs/metrics.md` に**散文で**書かれている（「malformed も
1 件と数える」「カバー率の分母は judgeable な質問」「ドメイン別獲得率は 100% にならない」）。
一方で **I3（質問別の合計＝グループの率）、I6（シェア列の丸め）、I8（件数の合計）は docs にもテストにも
無い**。つまりこの表は「担保されている式」と「口約束になっている式」の両方を含む。

実測（使い捨ての確認）: I1〜I5・I8 を確かめる乱択テストを `main` = `8603414` で回した（run と citation を
300 ケース生成し、グループごとに n <= d、質問別の合計、シェアの合計、カバレッジの重複、件数の和を検証）。
**すべて成立した**ので、表の「いまの担保」は現時点では事実。このテストはコミットしていない
（案 B で入れるものの下見）。意味があるのは「通った」ことではなく、**分母を変えた瞬間に落ちる形に
できる**ことで、これは Lean の証明では得られない性質。

## 2. 導入費用

見積もりは「入れる」「維持する」の 2 段で考える。

- **ツールチェーン**: Lean 4 と `elan`、`lean-toolchain` でバージョン固定、ビルドは Lake。
  Mathlib を使うなら `lake exe cache get` で数 GB 規模のキャッシュ取得が要る（使わない構成も可能）。
- **CI**: 現在は 3 OS のマトリクスで go vet / build / test、Linux で gofmt と `-race`、
  加えて golangci-lint と govulncheck。`make check` がその 1 本のゲート。証明ジョブを足すと
  ゲートが 2 本になり、OS マトリクスに Lean を載せるかの判断も要る（載せないなら
  「ローカルでだけ通る証明」が生まれる）。
- **レビュー可能性**: このリポジトリの強みは「Go のテストなら誰でも読める」こと。Lean の証明は
  読める人が限られ、**空虚な定理（前提が矛盾していて何でも真になる／主張が自明）**を見抜くには
  それなりの訓練が要る。`sorry` の混入と公理の汚染（`#print axioms` に `sorryAx`）を検査する
  仕組みを別途持つ必要がある。
- **維持**: モデルはコードを写したものなので、コードが変われば証明も直す。直さないと
  「通っているが古いコードについての証明」という一番危ない状態になる（デッキで言う
  *同期コミット* の管理。これは Lean でも TLA+ でも同じ）。
- **リリース経路**: Lean は証明にしか使わないので、バイナリには載らない（`aicm` は単一静的
  バイナリ・CGO 無しのまま）。この点は利点であり、`docs/architecture.md` の方針を壊さない。

## 3. 代替案の比較

| 案 | 何を保証するか | 反例が出るか | 追加依存 | この repo との相性 |
|---|---|---|---|---|
| **B. Go の fuzz + プロパティテスト**（stdlib のみ） | I1〜I5・I8（構成の性質）と I2・I9（算術）を実入力で。ドメインの fuzz も | 反例そのもの（入力値） | 無し | ◎ `make check` に足せる |
| **C. TLA+ / TLC を `internal/runner` に限定** | 操作順の不変条件（二重記録しない、失敗を再送しない、追記専用） | 反例（操作列） | TLC（Java）を開発時のみ | ○ 状態機械が実在する唯一の場所 |
| **D. Lean を最小スコープで PoC** | I2・I6・I9（丸めの上限と点差の合成則）と、正規化のモデル | 出ない | Lean 4 + elan | ○ 率の算術だけはモデルが忠実になる。それ以外は△ |
| **A. 何もしない** | 現状の 18 ファイルのテスト | — | 無し | ◎ いま困っていない |

推奨順は **B → C → D**。B は今日から入れられて、C は「順序で壊れる不具合が実際に出た」ときに
入れる。D は §6 のトリガが立つまで保留。

補足: 前掲のスライド（TLA+ / TLC + PStack）の流れ——モデル → TLC の反例 → 実コードで再現 →
回帰テスト——は、そのまま案 C の進め方であって、Lean を入れる話ではない。TLC の反例が
「操作列」として出るからこそ実コードの再現テストに落ちる。Lean の失敗は証明の失敗であって、
再現手順を運んでこない。

## 4. 案 B の中身（先にやるならこれ）

- `internal/domain`: `FuzzSplitCitationURL`（任意バイト列で panic しない、malformed は捨てずに残す、
  同じ入力は同じ dedupe key）、`CanonicalHost` の冪等性、`IsOwnDomain` のラベル境界
  （`subdomains=false` の非対称性を含む）。
- `internal/analysis`: 乱択した run/citation 集合から `Build` を回し、I1・I3・I4・I5 を確かめる。
  `NewRate(n, d)` が `d>0` で `0 <= Value <= 1`、`Text` と `Value` の一致、`Delta` の符号と加法性（I9）。
- `internal/analysis`: **`TestNoRateFormattingOutsideAnalysis`** を追加する。`analysis` 以外に `%.1f%%` が
  現れたら落とす（既存の `TestNoProviderSDKIsImported` と同じ形）。I2 の「再計算しない」を機械で守る。
- `docs/metrics.md`: I3・I6・I8（と丸めは小数 1 桁・.5 は偶数）を「読者が手で検算できる式」として
  短く載せる。I4・I5・I7 は既に散文で書かれているので、式の形に揃えるかは任意。
- CI: `-fuzztime` を短くした fuzz を PR で、長めを nightly で。`make check` の所要時間は増やさない。

## 5. もし Lean を入れるなら（スコープの切り方）

1. `proofs/` に独立した Lake プロジェクトを置き、Go のモジュールとは切り離す（`go build ./...` に混ぜない）。
2. `make proof` を追加し、CI では別ジョブ。`make check` には入れない（オフライン・高速の約束を守る）。
3. 対象は `internal/analysis` の率（`NewRate`・`Delta`・丸め）を先に、`internal/domain` の文字列境界を
   次に。率のほうがモデルが忠実で、定理（I2・I6・I9）も自明でない。
4. 率の入出力ベクタ（`n`・`d`・表示文字列）と、正規化の入出力ベクタを JSON で 1 か所に置き、
   Go のテストと Lean のテストが同じファイルを読む。これが「モデルと実装が同じ規則を指している」
   唯一の証拠になる。
5. `sorry` の禁止と `#print axioms` の検査を CI に入れる。空虚な定理を作らないための最低線。
6. モデルが一致したコミットを記録し、対象コードが変わったら証明を見直す（同期コミットの管理）。

## 6. 再検討のトリガ

次のどれかが起きたら、この検討を D 番号の決定としてやり直す。

- 率の定義を仕様として外部に公開し、**算術の定理**（I2 の丸めの一意性、I6 の上限、重み付き集計の整合）
  を主張したくなった。とくに「集計の定義を docs の式として固定し、実装がそれに従うことを証明する」
  という要求が出たら、Lean の出番になる。
- 正規化を RFC 3986 / UTS #46 への**準拠**として証明対象にしたくなった（この場合も Lean 単独では
  足りず、適合性テストが主役になる）。
- 検証済みのコアを他言語・他リポジトリに配る話が出た（Lean の抽出や C 経由の共有が意味を持つ）。
- 逆に、**順序で壊れる不具合が実際に出た**なら、Lean ではなく案 C（TLA+）を先に入れる。
