## 2. 決定事項（新規に記録する）

### D25 丸めの全数照合は `d ≤ 3000` を常設にし、独立した整数オラクルで回す（#8）

- 常設範囲は **`d ≤ 3000`, `n ≤ d` の 4,504,500 通り**。nightly へ逃がさない。
- 照合は `big.Rat`（`exactTenths`）を範囲全体に広げず、**別経路の整数オラクル**で行う:
  `lower = 1000n/d` を求め、`2000n` と `(2·lower+1)·d` を比較して中点の上下を決め、
  一致したときだけ `lower` の偶奇で決める。剰余を計算しないので、実装の
  `2*r` 比較の写し間違いを検出できる。
- `big.Rat` は **`d ≤ 300` の全数**（既存、約 0.01s）と **`d ≤ 3000` の全 tie 4,600 通り**
  に残す。速いオラクルが規則からずれていないことを、厳密計算の境界で毎回確かめる。
- 実測（Go 1.26.11 / darwin/arm64）: オラクル全数 **0.01s**、`big.Rat` 全数は **0.78s**。
  後者を常設にすると `go test ./...` が約 0.8s 伸びるため採らない。
- `make check` の増分は `internal/analysis` のテスト時間 +0.01s 程度で、`go test` は
  パッケージ並列なので全体の wall time はほぼ変わらない（実測は §5 に記録）。

### D26 競合の public suffix は設定検証で拒否し（exit 2）、既存値は消さずに `list` で示す（#11）

- `config.Problems()` が `competitors` の各値を検証し、public suffix を **exit 2** にする。
  `own_domain` と同じ扱いにする理由: どちらも「どのサイトを 1 行にまとめるか」を決める
  計測規則で、D23 以降は競合行がサイト単位（suffix 配下の全顧客を吸い上げる）だから。
  警告にしない理由: `run` の既定出力は進捗が多く、stderr の 1 行は見落とされる。
  `Problems()` は「計測を実行できない設定」を列挙する場所で、ここに入れると
  `aicm init --competitors github.io` も追加のコードパス無しで拒否できる。
- `Problems()` を呼ぶのは `run` と `init` だけなので、**既存の DB を読むコマンド
  （`report` / `trends` / `compare` / `export` / `verify`）は止めない**。既存の設定を
  直すまで新しい計測を始めない、という挙動にする。
- 既存の `competitors` 表（DB）の行は**自動削除しない**。`competitors list` は
  設定・DB の両方を従来どおり出し、public suffix の行に印を付ける（JSON は
  `invalid` を additive に追加）。`competitors remove` は今までどおり消せる。
- 正規化は `domain.CanonicalConfiguredDomain` に 1 つだけ置き、CLI の `normalizeDomain`
  と `config.Problems()` が同じ関数を使う。URL 形式で書かれた suffix も検出できる。

### D27 `trends` は隣り合うバケットの計測同一性を比べ、違えば差を出さない（#12）

- 各バケットは、そのバケットに入った run の `MeasurementIdentity` の集合を持つ。
- 直前のバケットと identity の集合が違う場合（`api_endpoint_version` /
  `question_set_sha256` / `tool_version`、空の値は「無い」なので比較しない）は、
  **`compare` と同じ語彙と文言**で `reason = conditions_differ`、`detail` に差分、
  cited / brand の差は出さない（`cited_delta` は null、`*_delta_text` は未測定マーク）。
- バケット自体が条件を混在させる場合は `mixed_conditions`（D24 と同じ項目名・語彙）を
  point に additive に出し、注記にも「計測条件が混在」と書く。率は出す（D24 §4）。
- 優先順位は `no_history` → `earlier_unmeasured` → `conditions_differ` → `n_differs`。
  既存の `n_differs` は条件が一致したときだけ今までどおり出す（挙動を変えない）。
- JSON 追加は `identities`（重複なし・固定順）と `mixed_conditions` だけ。既存フィールドは
  変えない。
- 文言は `compare` と共有するヘルパー（`conditionsDifferNote` など）に寄せ、EN/JA の
  写し違いを作らない。

## 3. BDD タスク一覧

各タスクは「入力 → 期待する振る舞い」の単位。正常系・異常系・エッジを含む。

### #8

**T8-1 全範囲の恒久照合（正常系・境界）**

- 入力: `d = 1..3000`, `n = 0..d` の全 4,504,500 組。
- 期待: `Tenths(n, d)` が独立オラクル `midpointTenths(n, d)` と一致する。
- 具体例: `(1,16) → 62`（`6.2%`、half-up の `6.3%` ではない）、`(23,80) → 288`、
  `(1,2000) → 0`、`(2999,2999) → 1000`、`(1,3000) → 0`、`(1499,3000) → 500`。
- 失敗時は `n` と `d` と両方の値を出す（`t.Fatalf`）。

**T8-2 オラクルを厳密計算に固定する（正常系・境界）**

- 入力: `d ≤ 300` の全数（既存の `TestTenthsMatchesExactRounding`）と、`d ≤ 3000` の
  全 tie 4,600 通り。
- 期待: `midpointTenths` が `exactTenths`（`big.Rat`）と一致する。tie の件数が 0 なら
  テストを失敗させる（走査が空になっていないこと）。
- 具体例: `(1,16)` は tie で偶数側、`(23,80)` は tie で切り上がり、`(1,2000)` は
  tie で 0 のまま。

**T8-3 決定の記録**

- D22 の「未検証 / 既知の限界」を「常設の全数照合になった」に更新し、D25 を追加する。
- `docs/metrics.md` の Formatting rules に、全数照合が `d ≤ 3000` で常設であることを 1 行足す。

### #12

**T12-1 バケットの identity（正常系）**

- 入力: 同じ `provider/model/stage` で、週 1 は `tool_version = 0.1.0+norm3`、週 2 は
  `0.1.0+norm3` の run。
- 期待: `trends --json` の各 point に `identities` が 1 件、`mixed_conditions` は空。
  既存フィールド（`n`, `cited_own`, `reason`, `detail`）は変わらない。

**T12-2 条件が違うバケットは差を出さない（異常系）**

- 入力: 週 1 `tool_version = 0.1.0+norm3`、週 2 `0.2.0+norm3`。
- 期待: 週 2 の point は `reason = conditions_differ`、`detail = "tool_version: 0.1.0+norm3 -> 0.2.0+norm3"`、
  `cited_delta = null`、`cited_delta_text = "— (not measured)"`、`brand_delta = null`、
  `note = "conditions differ, so no delta (…)"`。JA は「条件が違うため差を出さない（…）」。
- 同様に `question_set_sha256` と `api_endpoint_version` の差でも差を出さない。
- 比較するのは compare と同じ 3 項目: `question_set_version` だけが違っても差を出す。
- 両側とも identity が空なら差を出す（空は「無い」で、相違ではない）。

**T12-3 既存の `n_differs` を保つ（回帰）**

- 入力: 条件が同じで `n` だけ違う 2 バケット（既存 `TestTrendsNotesADifferentDenominator`）。
- 期待: 今までどおり `reason = n_differs`、`detail = "2 vs 1"`、差は出す。
- `earlier_unmeasured` と `no_history` の優先順位も今までどおり。

**T12-4 バケット内の混在（エッジ）**

- 入力: 同じ週に `tool_version` が 2 種類の run。
- 期待: `mixed_conditions = ["tool_version: 0.1.0+norm3, 0.2.0+norm3"]`、`identities` は 2 件、
  率と `n` は出したまま、注記に「計測条件が混在」が入る。

**T12-5 CLI と文書**

- `aicm trends` の表の note 列に `conditions_differ` の文言が出る（EN。JA はレポート）。
- `docs/metrics.md` の Comparing periods / Trends 節、`docs/cli-reference.md` の `trends` 節、
  `docs/architecture.md` の Measurement identity 節を更新する。D24 の「別 issue」を D27 で更新する。

## 5. 検証

| コマンド | 結果（2026-11-28、Go 1.26.11 / darwin/arm64） |
|---|---|
| `go test -count=1 ./...` | 成功。`internal/analysis` は 0.29–0.54s（ベースライン 0.331s と同じ範囲） |
| `go test -race -count=1 ./...` | 成功。`internal/analysis` 1.614s（ベースライン 1.599s） |
| `go vet ./...` / `go build ./...` / `gofmt -l .` | 出力が空 |
| `git diff --check` | 出力が空 |
| `make check`（ベースライン `891f900`） | **21.22s**（warm cache） |
| `make check`（全実装後） | **16.30s**（warm cache）、QA 再実行 **14.79s**（テスト結果が cached）。差は cache の状態で決まり、変更分ではない |

### #8 の増分（受け入れ条件）

- 追加したテストの実行時間: `TestTenthsMatchesMidpointOracleOverFullRange` **0.01s**
  （`-race` でも 0.01s）、`TestMidpointOracleMatchesExactRounding` **0.00s**。
  合計 **+0.01–0.02s**。`go test ./...` はパッケージ並列なので wall time への
  寄与はこの範囲。
- 比較した代替（`big.Rat` を `d ≤ 3000` に広げる）: 0.78s、`-race` で **8.92s**。
  `make check` は `test-race` を含むので、この案なら race ジョブが約 9s 伸びていた。
- `make check` の wall time はベースライン 21.22s → 16.30s → 14.79s と**短くなって**
  いる。これは 2 回目以降で Go と golangci-lint の cache が温まり、最後はテスト結果
  まで cached になったためで、変更の効果ではない。#8 の寄与は上記のテスト実行時間で
  測るのが正しい。

`make check` には `golangci-lint`（`$(go env GOPATH)/bin` にあり PATH 外）と govulncheck が
含まれる。今回はどちらも実行できた（0 issues / No vulnerabilities found）。
