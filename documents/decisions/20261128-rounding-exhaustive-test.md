# 率の丸めの全数照合を `d ≤ 3000` で常設にする（D25）

| 項目 | 内容 |
|---|---|
| 日付 | 2026-11-28 |
| 入力 | issue #8「率の丸めの全数照合を恒久テストにする（現状は使い捨ての走査で d ≤ 3000 を確認）」。D22 で厳密丸めにしたときの全数走査がコミットされていない |
| 前提 | D22（表示は `n` と `d` だけで決める。ちょうどの .5 は偶数側）、D21（Lean は算術のみ）、`CONTRIBUTING.md` の不変条件 1（率は必ず n を持つ） |
| 決定 | 常設範囲は **`d ≤ 3000`, `n ≤ d` の 4,504,500 通り**。`big.Rat` を広げず、**別経路の整数オラクル**で `go test ./...` に常設する。nightly には逃がさない |

## 決定

1. **常設範囲**は `d = 1..3000`, `n = 0..d`。率の分母は run 数で、現実の計測は
   `d` が数百程度だが、丸めは入力の大きさに依存しない規則なので、境界の多い
   小さい `d` だけでなく 4 桁まで固定する。
2. **照合の相手は独立した整数オラクル** `midpointTenths`。
   - `lower = 1000·n/d` を 1 回だけ求める。
   - `2000·n` と `(2·lower+1)·d` を比較して、比が中点より下・一致・上を決める。
   - 一致したときだけ `lower` の偶奇で決める（偶数側）。
   - `Tenths` は剰余 `r` を求めて `2r` と `d` を比べる。**違う計算経路**なので、
     片方の比較や tie-break の写し間違いで必ず食い違う。
3. **`big.Rat` は規則の錨として残す**。`d ≤ 300` の全数（既存の
   `TestTenthsMatchesExactRounding`、約 0.01s）と、`d ≤ 3000` の **全 tie 4,600 通り**
   （`TestMidpointOracleMatchesExactRounding`）。tie は丸めが分かれる入力なので、
   ここを厳密計算で固定すれば、速いオラクルが規則からずれていないことを毎回確かめられる。
4. **`-short` / build tag / nightly は使わない**。実測で全数 0.01s、`big.Rat` の
   錨も 0.00s なので、逃がす理由が無い。CI の 3 OS すべてで同じテストが回る。
5. **数を固定する**。tie の件数が 4,600 でなければテストを失敗させる（走査範囲が
   黙って狭まったことに気づくため）。

## 理由

- D22 の全数確認は一度きりの走査で、コミットされていない。規則を変える変更が
  入っても、`d > 300` の tie は `go test` では検出できなかった。
- `big.Rat` を `d ≤ 3000` に広げると 0.78s（この環境）。`go test ./...` はパッケージ
  並列なので全体は隠れるが、1 つの不変条件のために 0.8s は高い。整数オラクルは
  0.01s で、しかも実装と別経路なので検出力は落ちない。
- nightly に逃がすと、PR の時点で規則違反が入る。D22 の食い違いは 553 通りあり、
  その大半は「気づかないままリリースされる」種類のもの。常設にする価値がある。

## 検討した代替案

| 案 | 却下理由 |
|---|---|
| `big.Rat` のまま `d ≤ 3000` を常設 | 0.78s。検出力は上がらない（オラクルと同じ規則を、同じ厳密計算で確かめるだけ） |
| `d ≤ 3000` を nightly / `-short` でスキップ | 規則違反が PR を通過する。CI は 3 OS で回っており、0.01s を惜しむ理由が無い |
| `d ≤ 1000` まで常設 | 「`d = 2000` が 415 件」という D22 の実測（いちばん偏る分母）を含められない |
| オラクルだけにして `big.Rat` をやめる | オラクル同士では「両方同じ間違い」を検出できない。厳密計算の錨は 1 つ要る |

## 影響

- テストのみ。表示・JSON・スキーマ・`aicm export` の列は変わらない。
- 追加: `internal/analysis/metrics_test.go` の
  `TestTenthsMatchesMidpointOracleOverFullRange`（0.01s）と
  `TestMidpointOracleMatchesExactRounding`（0.00s）。既存の
  `TestTenthsMatchesExactRounding` と `proofs/rate-vectors.csv` はそのまま。
- `make check` の増分は `internal/analysis` のテスト +0.01s 程度。実測は
  `documents/plan/20261128-issues-8-11-12.md` §5 に記録する。
- 入力の範囲を広げるときは、`isExactHalfway` の件数（4,600）も同じコミットで更新する。

## 未検証 / 既知の限界

- `d > 3000` は常設の全数照合の外（`proofs/rate-vectors.csv` の抜き取りと、
  大きな `d` の overflow テストだけ）。`d` は run 数なので 4 桁を超える計測は
  現実には無いが、規則としては上限を決めていない。
- オラクルは `n ≤ d` を前提にする（率の分子は分母の部分集合）。`n > d` は
  `NewRate` の呼び出し側が作らない。
