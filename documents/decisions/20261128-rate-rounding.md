# 率の丸めを比から計算する（D22）

| 項目 | 内容 |
|---|---|
| 日付 | 2026-11-28 |
| 入力 | オーナー「Lean 導入でバグが見つかったのか？」への回答で、仕様（偶数丸め）と実装（float64 依存）の食い違いを提示。案 B（実装を厳密丸めにする）を承認 |
| 前提 | D21（算術を Lean で証明）、D19（export は公開契約）、D8（率の分母と定義） |
| 決定 | **表示は `n` と `d` だけで決める。** `NewRate` の `Text` と `Delta` を整数演算にし、float64 は比 `Value` にだけ残す |

## 決定

1. `NewRate` の `Text` は `Tenths(n, d)`（`1000·n/d` を四捨五入、ちょうどの .5 は偶数側）
   から作る。`Value` は比の float64 のまま。
2. 差分は「表示された tenths の差」に揃える: `DeltaTenths(a, b) = Tenths(b) − Tenths(a)`。
   JSON の `delta` もこの値の 1/10 pt 単位になる。
3. 共有ベクタに tie 族を追加する: `d ≤ 32` の全通り + `d ≤ 1000` の全 tie + `d = 2000` の
   全 tie + 大きな `d` の抜き取り（計 2944 行）。
4. Lean の `tenths` / `deltaTenths` は変更なし。**もともとこの規則を書いていた**ので、
   コードをモデルに合わせた。

## 理由

- 表示が `float64` の表現可能性に依存するのは、この計測器の再現性の約束に反する。
  同じ `n` と `d` が環境や Go のバージョンで別の tenth になる。
- 実測: `d ≤ 3000`, `n ≤ d` の 4,504,500 通りで、ちょうどの .5 は 4,600 通り、そのうち
  **553 通り（12%）** が偶数丸めと違う tenth を出していた。最小は `23/80`（`28.7%` 対 `28.8%`）。
  偏りは `d = 2000`（415 件）と 80 の倍数。
- 差分を「表示の差」にすると、表を手で引ける（`81.2% − 20.0% = +61.2pt`）。厳密差を
  丸めると表と食い違う（`1/5 → 6/32` で `−1.3pt` 対 表の差 `−1.2pt`）。
- これは D21 で入れた証明を満たす方向の修正で、モデルを弱めるものではない。

## 影響

- 表示が変わるのはちょうどの .5 の入力だけ（旧実装で float が外れた 553 通りと、
  同種の差分）。書式（`%.1f` 相当、`+`/`-` 符号、`pt`）は変わらない。
- `text`・`cited_delta_text`・`brand_delta_text` は export の契約（D19）だが、変わるのは
  丸めの境界だけで、列は増減しない。
- テスト: `TestRateRoundsTheRatioNotTheFloat`（23/80 など）、
  `TestTenthsMatchesExactRounding`（`big.Rat` と `d ≤ 300` の全数照合）、
  `TestDeltaIsTheDifferenceOfThePrintedRates`。`make proof` は 2944 行を照合する。
- 率の分母・カバレッジ・シェアの定義は不変（D8 維持）。

## 未検証 / 既知の限界

- 全 `d ≤ 3000` の一致は一回の走査で確かめた（恒久テストは `d ≤ 300` の全数とベクタ）。
- JSON の `delta` は tenth 単位に量子化される（以前は float の全精度）。細かい桁を期待する
  consumer には影響がある。
- tie の向き（偶数側）を変えるときは、コード・`docs/metrics.md`・`proofs/Rate.lean`・
  `rate-vectors.csv` の 4 つを同じコミットで揃える。
